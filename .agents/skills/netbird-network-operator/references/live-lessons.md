# 脱敏实战经验

这些经验来自本仓库相关的真实配置、升级和排障会话，已经移除客户名称、真实地址、凭据和敏感拓扑。它们补充文档中的通用步骤，不把某次现场值当成固定模板。

## 1. 团队访问收敛

当用户要求旧新配置不能并存时，正确顺序是：

1. 盘点旧组、旧 Policy、旧 Key、现有 Peer 和所有依赖。
2. 创建目标团队组，先迁移现有 Peer。
3. 按数据库、域名、VPC 等职责创建独立最小 Policy。
4. 创建有资产含义的 One-off Key，不保存明文。
5. 验证目标组的 Peer、Policy、Key 精确数量。
6. 经授权删除旧 Policy、旧 Key 和旧组，再次确认旧行消失且目标行仍存在。

Dashboard 的成功提示不能证明收敛完成。必须重新加载列表和详情，用精确名称与数量验证。

## 2. 浏览器自动化

Dashboard 导航和角色选择器在页面尚未完成加载时可能超时。不要持续重试旧 selector；获取新页面状态，使用当前可见导航元素继续。`/routes` 等凭记忆构造的地址可能不是当前实际入口，应以页面和官方文档为准。

## 3. 定向公网出口

看到某个 Peer 在线、属于候选组且自身能访问公网，只能说明它可能成为 Routing Peer，不能证明：

- Network / Route 已正确绑定。
- 目标只对指定来源组分发。
- Pod / 容器有正确的公网 SNAT。
- 目标实际看到获准公网 IP。

上线必须验证客户端路由、Routing Peer 计数和目标侧来源 IP。若尚未完成这些证据，只能报告“发现候选路径”，不能报告“定向出口已完成”。

## 4. Standalone Routing Peer

`NB_USE_NETSTACK_MODE=true` 改变隧道数据面，但容器使用 host 网络时仍与宿主机共享网络命名空间。在多用途 Docker 主机上，已验证的安全默认是独立 bridge + Userspace，并从业务容器内部对比 DNS、SNAT、TCP 和重启次数。

公网 IP 能访问不代表 VPN 私网数据面可用。客户端 LAN `/24` 与远端 VPC `/16` 重叠时，最长前缀会把流量留在本地；用 `/32` 或非重叠目标并检查实际路由、传输计数或抓包。

## 5. Kubernetes Routing Peer

回滚审计需要同时看 Dashboard、Routing Peer 主机、Kubernetes 节点和真实 TCP。临时 Route / NAT 是否清除，要在每个相关层确认；一个备用 Peer 离线表示冗余下降，不等于主路径已经故障。

UDP 请求发往网段网络地址等无效目标可能产生错误，不应直接归因于 K8S 路由。沿实际源、目标、协议和错误归属定位。

## 6. 控制面升级

外部 IdP 的 Legacy 多容器架构不能因为官方出现 combined 模式就强制迁移。先确认迁移工具是否支持当前 IdP 和数据库；不支持时保留架构，只升级获准核心组件，并验证备份完整性、数据库、OIDC、原 Peer 身份、策略和真实业务。

`status --check ready` 可能早于 Networks 和路由收敛。Routing Peer 升级后要继续等待完整状态、原身份、Resource、路由、真实 TCP 和计数恢复，再升级下一个。

## 7. Setup Key

Setup Key 注册机器，不是共享人员账号。长期办公设备优先每机 One-off；Reusable 只用于短期批量注册，usage limit 等于计划设备数，完成后立即撤销。Key 过期或撤销不影响已注册 Peer，因此不需要为了“长期使用”保留无限期 Key。

One-off 的语义就是单次使用，不能把它和大于 `1` 的 usage limit 组合。NetBird v0.77.1 起，这类 Public API 请求会返回 HTTP `422`，不再静默把上限改成 `1`；批量注册应显式改为 Reusable，并在完成后撤销。

已使用的 One-off Key 不能恢复明文或改名。命名和资产备注要在创建前设计好；任何长期记录只保留 Key 名称、状态和关联对象，不保留值。

## 8. Policy API 端口表达

同一条 Policy 规则不能同时提交 `ports` 和 `port_ranges`，创建和更新都会以 HTTP `422` 拒绝。自动化需要把单端口和区间混在一条规则时，统一写成 `port_ranges`：单端口使用相同的 `start`、`end`，不要根据 Dashboard 的视觉输入推断 API 可以混用两个字段。

## 9. 不要把应用故障误判为网络故障

请求经过 NetBird 后出现 API 500、缓存错误或异步异常，不代表隧道故障。若 TCP 已成功到达应用，应继续关联拥有该错误的服务日志和数据库错误。例如字段缺失属于 schema / migration 问题，重部署应用或修改 VPN 都不会修复。

## 10. 间歇超时与中继传输

- 同一开发机多个服务响应变慢时，先用路由节点直连、同一时段应用探测及隧道/
  出口包头对照。读取真正拥有socket的容器网络命名空间，宿主机累计重传不能替代。
- 旧内核的tcp_tw_recycle与NAT时间戳可导致SYN到达容器但没有SYN-ACK；用
  PAWSPassive/ListenDrops增量支持单项修正，不批量统一其他TCP参数。
- TCP端口范围不会放行UDP；公网Routing Peer的实际WireGuard端口常见51820。
  新规则后应重新验证ICE/P2P，不能只看到安全组保存成功就宣布恢复。
- 独立Relay缺TLS时可能只有WS监听；Caddy HTTP/3占用UDP443不等于QUIC已启用。
  协调端口归属、受校验的TLS上游和证书续期，不跳过验证，不拆成两个无共享会话的Relay。
- 文件证书更新不一定自动重载；按有效证书与实际服务指纹决定是否只重启Relay。
- 不能将P2P应用探测写成QUIC中继压测；WS101也不等于完整认证/回退数据面。

## 11. 升级与离线镜像交付

先核心组件、后QUIC改造、再逐个Routing Peer，每阶段有独立回滚点。保留外部IdP，
先核验SQLite在线备份及对象数量。Kubernetes双节点先用OnDelete控制单节点替换，
确认身份、资源、Pod/Service/NodePort/外联和监控后再继续；最后恢复原更新策略并
保存可用声明清单。只清理或重建获准的路由实例，不因离线旧Peer存在就删除对象。

镜像仓库写入拒绝时，不扩大权限或换成latest；可交付已核验官方归档，比较SHA256
和导入image ID，并记录新节点需要预置镜像。Compose v1必要时只停、删、建对应
Routing Peer容器，保留独立身份和同机业务；不要通过重启Docker解决旧工具重建问题。
